# OSS/VOC 자동화 조사

조사 기준일: 2026-09-10. 범위는 현재 Python 3.9+ 표준 라이브러리 스캐폴드에 실제로 재사용할 수 있는 코드·프로토콜·템플릿이며, 공개 1차 소스의 저장소, manifest, LICENSE, 공식 문서/API와 실제 템플릿 JSON만 확인했다. 패키지는 설치하거나 실제 Jira/LLM 호출을 하지 않았다. 아래의 “확인”은 소스에서 읽은 사실이고, “권고”는 이 프로젝트의 [제품 범위](PROJECT_OVERVIEW.md)와 [실행 경계](ARCHITECTURE.md)에 적용한 판단이다.

## 결론

- **현재 채택:** 현재의 `opencode run --format json` subprocess 경계, stdlib/SQLite runtime, 네 개의 공유 local skill만 유지한다. evidence event마다 OpenCode process 하나를 실행하되, 한 process의 stream에는 auxiliary event/title이 포함될 수 있고 “provider HTTP 요청 정확히 한 번”을 계약으로 삼지 않는다.
- **미설치·향후 후보:** `atlassian-python-api==5.0.4`가 향후 Jira adapter의 우선 후보지만, 실제 ACL/auth/server flavor가 없는 현재에는 설치하거나 구현에 채택하지 않는다. 이 라이브러리는 JQL·issue·comment·Jira Service Management 호출을 제공하지만 ACL, evidence cap, retry/dedupe, 게시 lifecycle은 제공하지 않는다.
- **선택적 향후 평가:** 저장된 OpenCode 결과를 검사할 때 `promptfoo==0.122.2`를 Node 22 이상 격리 eval job에서만 검토한다. 현재 설치하지 않으며, n8n/Activepieces flow는 deterministic 단계·human-review 설계 참고로만 보고 template code는 가져오지 않는다.
- **보류/거부:** `pycontribs/jira==3.10.5`는 현재 Python 3.9 scaffold에 직접 설치할 수 없고 별도 object surface가 있어 지금은 보류하지만, Python floor 변경 자체를 영구 금지 사유로 삼지는 않는다. OpenCode JS SDK/serve와 Inspect AI는 별도 lifecycle/실행 부담 때문에 보류하고, `mcp-atlassian==0.23.1`은 광범위한 agent-facing 표면·큰 의존성·보안 advisory 이력 때문에 runtime connector로 거부한다.

## 실제 VOC/support-ticket template 확인

### n8n: Jira support triage/resolution

- 공식 template 설명: [Automate support ticket triage and resolution with JIRA and AI](https://n8n.io/workflows/3868-automate-support-ticket-triage-and-resolution-with-jira-and-ai/).
- 공개 template API [JSON](https://api.n8n.io/api/templates/workflows/3868)를 읽어 `workflow.workflow.nodes` 27개와 connections 21개를 확인했다(저장/실행/credential 사용 없음). 실제 노드에는 Schedule Trigger, Jira `Get Open Tickets`, `Remove Duplicates/Mark as Seen`, structured LLM `Label, Prioritize & Rewrite`, Jira update, similar resolved issue 검색, comments 수집, resolution 요약, `Attempt to Resolve Issue`, Jira `Add Comment to Issue`가 모두 있다.
- **재사용 가능한 부분:** 우리 pipeline의 단계 분해(수집→dedupe→정규화→similar evidence→요약/추천→human review)와 idempotency marker 설계다. **재사용 금지:** 템플릿의 OpenAI/Jira credentials와 ACL·승인·write ownership을 검증하지 않은 실행 그래프. template별 author/사용조건은 별도로 확인되지 않았으므로 JSON을 제품에 복사해 license가 해결됐다고 가정하지 않는다.

### Activepieces: HubSpot customer support ticketing

- 공식 template API [JSON](https://cloud.activepieces.com/api/v1/templates/miLjdP1BihsBes8EzexpT)는 `Customer Support Ticketing` (author `Activepieces Team`, updated `2025-12-28`)의 실제 flow를 반환한다. `new_ticket` trigger → AI rewrite → AI category(Sales/Tech/Customer Support) → router → 담당자별 Slack direct message라는 end-to-end 구조이며, JSON에서 piece/version, prompt, branch condition, connection placeholder를 직접 확인했다.
- 공식 [Jira Cloud piece](https://raw.githubusercontent.com/activepieces/activepieces/main/packages/pieces/community/jira-cloud/src/index.ts)도 `createIssue`, `updateIssue`, `searchIssues`, comments, transition, new/updated issue triggers를 실제 source로 제공한다.
- **재사용 가능한 부분:** trigger/action mapping, schema/branch 형식, human notification 단계. **재사용 금지:** template의 `gpt-4o`, connection IDs, recipient IDs, ACL·승인 없이 AI 단계와 외부 write 단계를 연결한 정책. 이 template은 실행 검증이나 내부 ACL 증명이 아니며, 실제 provider/Jira 호출을 이번 조사에서 하지 않았다.

두 template은 “실제 flow artifact가 있는” 상용 자동화 사례이지 이 프로젝트의 production-ready 구현이나 OSS license 보증이 아니다. 둘 다 우리 구조에서는 정적 adapter/검증 가능한 proposal 뒤에 두고, 자동 Jira write는 별도 승인된 integration slice로 남겨야 한다.

## SDK 대 subprocess와 내부 LLM/ACL 경계

현재 adapter가 사용하는 CLI는 raw JSON events를 내므로 Python이 process lifecycle, timeout, malformed/truncated stream, error event, terminal completion을 판정해야 한다. 이것은 completion parser 유지 비용이지만 Python 3.9 스캐폴드에 persistent service를 추가하지 않는 단일 경계다.

OpenCode SDK의 structured output은 schema 검증과 기본 retry를 제공하므로 장래 service에서는 parser 중복을 줄일 수 있다. Python은 `opencode serve` HTTP API를 직접 호출할 수 있어 Node bridge가 필수는 아니지만, persistent server의 health/auth/shutdown/timeout/log lifecycle을 추가로 운영해야 한다. 따라서 **현재는 CLI를 유지**하고, 해당 lifecycle 비용을 감당할 필요가 생길 때만 serve/SDK를 단일 호출 경계로 전환한다. SDK를 채택하더라도 OpenCode plugin은 Jira 도구를 추가하지 않는다.

내부 LLM endpoint/model 설정이 OpenCode provider contract와 호환되는지는 이 조사만으로 확인되지 않았다. 실제 ACL/principal을 얻기 전에는 connector가 어떤 project filter도 authorization으로 해석하지 않으며, Jira 본문·검색결과는 prompt injection 가능한 비신뢰 데이터로 다룬다. 즉 허용 순서는 `trusted principal/ACL → Jira query/filter → evidence cap → heuristic OpenCode call → schema/evidence validator`이며, OpenCode를 호출할 수 있는 단계는 semantic symptom/remediation 문장 같은 heuristic뿐이다.

## 다음 구현의 최소 probe

이번 문서 변경에서는 package 설치·외부 호출·코드 변경을 하지 않는다. 현재 commit에는 runnable Jira adapter가 없으며, 실제 ACL/auth/server flavor가 확보된 뒤 별도 integration slice에서 아래를 실행한다.

1. `atlassian-python-api==5.0.4`를 optional extra로 고정하고, `JiraPort`를 `search_issues/get_issue/get_comments` 읽기 전용으로 시작한다. fake HTTP/session fixture로 ACL/JQL allowlist가 library 호출보다 먼저 실행되는지, pagination/429/5xx bounded retry와 event marker가 동작하는지 검증한다. write method는 Port에 넣지 않는다. 실제 연결 계약이 없으면 이 단계를 시작하지 않는다.
2. OpenCode의 synthetic `--format json` event fixture를 추가해 success/error/timeout/malformed/truncated 각 terminal path를 기존 parser에 회귀시킨다. 실제 provider·Jira 호출 없이 현재 evidence/no-evidence 분기를 모두 통과시킨다.
3. 저장한 proposal/model output만 Node `>=22.22.0` 격리 job의 `promptfoo@0.122.2`에 넣어 allowed labels, max recommendations, known evidence ID, token-overlap, empty-evidence no-call을 assertion으로 검사한다. Promptfoo output에는 운영 원문·token·prompt secret을 넣지 않고 fixture를 사용한다.
4. n8n/Activepieces template는 import하지 않고, 필요한 단계만 Mermaid/fixture로 재현한다. 실제 connector/Jira write가 필요해지는 시점에만 별도 ACL·reconciliation·approval 계약과 license inventory를 통과시킨다.

## 현재 스캐폴드가 commit 전에 바꿀 것

이 docs-only pass에서 runtime을 바꾸지 않는다. 이 문서와 현재 기준선은 먼저 commit할 수 있으며, 이후 실제 ACL/auth/server flavor가 준비된 별도 integration slice에서만 (a) production ACL이 아님을 명시한 synthetic `project ==` 경계를 그대로 유지하고, (b) `atlassian-python-api`를 optional thin adapter로 평가하며, (c) OpenCode subprocess parser와 no-evidence provider 생략을 유지한다. `pycontribs/jira`, `mcp-atlassian`, n8n/Activepieces runtime, Inspect AI, OpenCode plugin/SDK를 현재 `pyproject.toml` 기본 의존성에 넣지 않는다.

의존성을 실제로 채택할 때는 lock/manifest와 함께 MIT/BSD-2-Clause/Apache-2.0 notice를 보존하고, Activepieces/n8n처럼 전체 제품 license가 단일 permissive OSS가 아닌 경우 subtree와 배포 범위를 기록한다. 이 문서의 버전·release 날짜는 조사 당시 공개 source 기준이며, 구현 PR 직전에 release/manifest와 transitive license를 다시 확인한다.
